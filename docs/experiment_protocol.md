# 實驗紀錄與實作規範

## 每次執行應保存

- 日期、環境 ID、來源 commit 或 SHA-256、完整編譯及執行指令。
- 編譯器／標準函式庫／libm 版本、CPU／架構、OS／WSL 版本。
- 最佳化、fast-math、FMA contraction、ISA 旗標；是否啟用 LTO。
- 輸入、seed、筆數、暖機次數、重複次數、原始輸出及退出碼。
- 電源模式、插電狀態、背景負載、核心綁定與溫度條件（可取得時）。

## Q1 benchmark 設計要求（待實作）

1. 從執行期輸入建立資料，固定 seed，公開產生方法。選擇各型態都能表示的起始值；避免計時期間的 I/O、配置與亂數產生。
2. 分開測相依運算鏈（延遲）、多個獨立 accumulator（吞吐量）及陣列（可能包含記憶體成本）。不要把結果混成單一「浮點數速度」。
3. 每個回合消費並輸出 checksum，搭配適合 GCC 的 optimization barrier 或獨立 translation unit；**僅輸出 checksum 不保證迴圈不被代數簡化**。檢查最佳化後的組合語言，確認待測運算仍在迴圈內。
4. 不要讓每次運算都讀寫 volatile，否則測量也包含 volatile 記憶體存取。barrier 本身的成本必須說明。
5. 使用 `std::chrono::steady_clock`，先暖機，多次量測，保留全部樣本並報告中位數與離散程度。計時足夠長以降低 timer 成本；交替或打散型態順序。
6. 明確區分 scalar 與 SIMD；檢查 vectorization report 和反組譯。相同元素數與相同 bytes 的比較回答不同問題。
7. 防止數值逐步 overflow、underflow、變成常數或 subnormal；先在計時外檢查值域與有限性。不要把無效資料當成速度成果。
8. 精度另做實驗：指定可信參考值／解析答案及其限制，報告絕對與相對誤差；參考值為零時不使用相對誤差。long double 不自動等於精確答案。

## 各題待查證重點

- Q2：先確定實際 libm 與來源版本。將 C++ overload 規格、平台函式庫演算法、CPU 指令三層分開；讀到某個來源檔案不能證明執行時走該分支。
- Q3：只改 fast-math；執行期資料避免 constant folding。針對候選反例檢查產生碼，並從對應 GCC 版本文件查實際啟用選項。不要宣稱所有 IEEE 754 行為都由單一旗標控制。
- Q4：比較的是實際儲存值的格式化，而不是原始十進位字串；精確 tie、鄰近值及負值分別測試。若測其他 rounding mode，檢查 `fesetround` 是否成功並記錄函式庫行为。
- Q5：相同程式碼、編譯器版本與旗標是必要條件。記錄 target/ABI；不能靠不同參數、未初始化值、資料競爭或其他 UB 製造差異。若平台 long double 相同，候選例子不成立，應保留此負結果。
- Q6：只有已量測的現象才能寫成結論；理論與推測要標示。新增求和實驗若與其他題重複，改選尚未討論的細節。
